本报告从详细设计（Detailed Design）视角拆解 LLM-WIKI：一个由 LLM 驱动、可自组织生长的知识库问答系统。系统接收原始文档（raw），通过多阶段 Agent 流水线将其"编译"为结构化的 Wiki 页面，以 Schema 宪法约束 AI 行为的边界，并通过问答、体检、共治等闭环让知识体系持续演进。

1. 项目概览与定位

1.1 一句话定位

LLM-WIKI = 知识编译流水线 + Agent 自主执行引擎（Harness） + 治理/共治体系。它不是"聊天机器人 + 文档库"，而是一套把散落资料持续转化为可信、可检索、可演进的组织知识资产的自动化平台。

1.2 知识编译隐喻（核心设计隐喻）

整个系统围绕一条"编译链"建模，每一层的产物都是下一层的输入，层级之间严格隔离：

图 1.1 知识编译隐喻：raw → parsed → wiki → schema，schema 反向约束编译过程
  • raw → parsed：源文件不可变（只允许新增），通过 Python 子进程（doc_parser.py）抽取为结构化中间产物；
  • parsed → wiki：LLM 编写器（WritingAgent）把中间产物"编译"为 Wiki 页面，必须通过 WriterOrchestrator 的四道验证把关链（写入 → 合规检查 → 质量验证 → 异步一致性调和）；
  • wiki → schema：沉淀出的构建规则（Schema）成为"宪法"，经 SchemaInjector 强制注入所有 Agent 的 Prompt，反向约束解析与写作行为。

2.3 门面模式：单一入口的 HarnessEngine

领域层用 HarnessEngineImpl 作为唯一的"Agent 执行门面"，应用层不直接接触任何 Agent 或流水线细节：

public class HarnessEngineImpl {
    // 摄入流水线：UPLOAD → ANALYZE → REVIEW → EXECUTE
    public ExecutionModel executeIngest(Long scopeId, Long sourceId) {
        return pipelineOrchestrator.runIngestPipeline(scopeId, sourceId);
    }
    // 问答流式：两 Agent 两阶段（Fact → Synthesis）
    public Flux<String> executeQueryStreaming(Long scopeId, String question, String sessionId, boolean deepMode) {
        return agentRunner.runQueryAgentStreaming(scopeId, question, sessionId, deepMode);
    }
    // 体检流水线：八步 Lint
    public ExecutionModel executeLint(Long scopeId, boolean fullScan) {
        return pipelineOrchestrator.runLintPipeline(scopeId, fullScan);
    }
    // 问答结果落库：四步 Save
    public WikiPageDO executeSaveQueryResult(Long scopeId, String question, String answer, String sessionId) {
        return pipelineOrchestrator.runSaveQueryResultPipeline(scopeId, question, answer, sessionId);
    }
}
为什么用门面？① 应用层只依赖一个稳定接口，Agent 数量/流水线步骤的增减不影响上层；② 门面内置 rateLimitService.tryAcquireConcurrent(scopeId) 等前置治控，保证所有 AI 执行路径都过同一道闸；③ 便于 TokenUsage 统计与执行追踪切面统一挂载。

2.3 领域边界与类图关系（DDD 视角）

本章从 DDD 限界上下文视角给出系统的领域边界总览与三张类图关系：领域模型（聚合根/Entity）、领域服务执行引擎、治理与工具调用管道。每张图的 namespace 分区即领域边界，note for 注释标注聚合根与关键类的职能、状态机与不变量。事实来源：domain/model（13 个领域模型，按 system / harness / wiki 三子包）与 domain/service（168 个领域服务）。

4.1.2 流水线与状态机（代码级）

  • 状态机：uploaded → analyzing → awaiting_review → executing → done｜终止态：failed / cancelled / paused。

  • 五种诊断类型：orphan（孤儿页：无来源/无链接引用）、stale（内容过期：源更新后页面未同步）、missing_crossref（缺失交叉引用）、conflict（语义冲突：与既有页面矛盾）、gap（覆盖缺口）。

4.4.2 代码级要点

  • 为什么是"宪法"：所有 Agent（Fact / Synthesis / Writer / LintProbe）的 System Prompt 都通过 SchemaInjector.prependForQuery(scopeId, prompt) 前置注入 Schema 内容——没有办法绕过，Schema 就是知识库的"构建配置宪法"。

5.3 可靠性三支柱

① 异步分发（MQ 或本地）

执行任务优先投递 RocketMQ（pipeline task / control / lint schedule 三个 Topic），MQ 不可用则回退本地线程池 —— 外部依赖可降级。MqHealthService 监测链路健康度。

② 断点续传 + watermark

Ingest 失败可从失败步骤 resume；Lint 用 watermark 游标（cursor / signature）支持增量续检与报告短路 —— 长流水线可中断可恢复。

③ 可追溯日志链

ExecutionTracker 管执行状态；ExecutionHistoryService / ExecutionEventLogService 记事件流（TURN_START / STEP / ERROR / TURN_END）；TokenUsageDailyService / TokenUsageMonitor 沉淀用量。所有 AI 行为都可回溯到 execution_step 与 token 明细。

6. 设计理念与为什么（架构决策的因果链）

#设计决策解决什么问题为什么这么设计（因果）
1 知识编译隐喻
raw→parsed→wiki→schema 逐层编译		 LLM 输出不可信、不可控、不可回溯 仿照编译器：源头不可变 + 中间产物 + 目标产物 + 规则约束。任何一层错误可定位到上一层输入，且 schema 反向约束编译过程，形成闭环内省而非单向"生成即丢弃"。
2 Agent 自主导航，而非静态 RAG
Fact Agent 带 7 个工具自主检索		 静态检索（top-k 段落）难以回答跨页、多跳、需精确读取源文件的问题 预检索（preRetrieveLight）只做轻量起点，真正的导航权交给 Agent（读页/查源/列页/查相关页），Layer1 事实骨架 + Layer2/3 综合的分层产出保证"先立事实、后做综合"，减少幻觉。
3 两阶段人机协同
摄入/体检都留人工闸门与审批级别		 AI 自动化的正确性风险 把错误的代价前置：分析阶段（廉价、无副作用）允许失败；执行阶段（贵、有副作用）必须过闸。approval_level 让不同 scope 可配置自动化程度——信任度高的团队可全自动。
4 Schema 共治宪法
无人直接手编、版本化、注入所有 Agent		 Prompt 漂移、知识库风格失控、规则散落各处 Schema 成为单一事实源（SSOT），7 段骨架强制结构，补丁由 Lint 发现驱动 —— 规则随知识库共同演化，而非管理员写死。注入（而非拼接参考）保证不可绕过。
5 增量 + watermark + 报告短路 LLM 成本随知识量线性爆炸 Lint 只扫变更页（filterCacheMissPageIds）、游标续检、signature 一致则跳过 LLM 重的建议步骤 —— 把浪费降到趋近 0，让"每天体检"在经济上可持续。
6 准确性优先的降级链
查询失败自动回退简单模式		 Agent 管线不稳定会阻塞用户 一切外部失败（模型不可用/预检索失败/流中断）都 onErrorResume 回退 runSimpleQuery —— 用户永远得到回答；复杂能力的成功率低于简单模式时，自动降级是产品体验的底线守卫。
7 DDD 分层 + 门面 + 编排器 Agent 数量与流水线步骤膨胀导致代码纠缠 web→biz→domain 单向依赖、HarnessEngine 门面收敛入口、PipelineOrchestrator 集中状态机 —— 把"过程"（pipeline）与"能力"（agent）分离，每类步骤可独立替换、并行、排序，业务语义在 domain 层沉淀。
8 治理四件套全路径闸门 多 Agent 并发下预算击穿、越权读写、死循环 RateLimit/Barrier/Approval/TokenUsage 不是"可选优化"而是执行前置条件（门面内置 tryAcquireConcurrent），配合 ToolExecutionPipeline 八过滤器 —— 让 LLM 在高自由度下仍处于可预期边界内。
一句话总结设计哲学：LLM-WIKI 不是"把 AI 塞进知识库"，而是把知识库建模为一个可编译、可体检、可治控的软件系统——LLM 只是其中受约束的执行单元，正确性靠"编译链 + 闸门 + 验证 + 宪法"系统性保证，而非寄望于单次提示词。
